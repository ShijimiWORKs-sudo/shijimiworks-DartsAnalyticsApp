# キャリブレーション検証報告（§7）

最終更新: 2026-09-17

## 要求事項（指示書§7、原文要約）

確認対象: board plane / bull center / board radius / segment boundary /
homography / lens distortion / camera parameters。キャリブレーション結果を
保存し、精度低下時には再キャリブレーションを促す。直接測定値・計算値・
推定値・助言を明確に区別する。

## 実装状況（確認対象ごと）

| 確認対象 | 状態 | 詳細 |
|---|---|---|
| **bull center** | 実装済み（簡易） | `board/calibration.py`の`calibrate_from_image`が、閾値二値化＋最大連結成分の重心を「盤の中心」として検出。ダーツボード固有のブル検出（リング検出等）ではなく、盤全体の形状重心を近似的に用いている。 |
| **board radius** | 実装済み（簡易） | 検出領域の面積から等価円半径`sqrt(area/π)`を算出。 |
| **board plane** | **未実装** | カメラが盤面に対して正対していること（傾き無し）を前提とした2D処理のみ。盤面の傾き（plane）を検出・補正する処理（例：楕円フィッティングで傾きを推定し補正する等）は無い。 |
| **segment boundary** | **未実装** | セグメント（各数字エリア・シングル/ダブル/トリプルの境界）の検出・整列は無い。`board/coordinates.py`の`angle_deg`はセグメント境界に対して未整列（モジュールdocstringに明記済み、Phase 4以降の拡張候補として先送り）。 |
| **homography** | **未実装** | 射影変換（斜め方向からの撮影を正面画像相当に補正する処理）は無い。calibrationは平行移動＋等方スケーリング（中心＋半径）のみのモデルであり、盤面が画面に対して傾いている場合の歪みは補正されない。 |
| **lens distortion** | **未実装** | スマートフォンカメラの広角レンズ歪み（樽型/糸巻き型歪み）の補正は無い。 |
| **camera parameters** | **未実装** | 焦点距離・センササイズ等のカメラ内部パラメータの推定・保存は無い。 |
| **結果の保存** | **今回実装**（§10と連携） | `SqliteCalibrationRepository`（§10で新規実装）が`board_calibrations`テーブルへの保存・取得に対応。`session_id`と紐付けて保存可能。 |
| **精度低下時の再キャリブレーション促し** | **今回新規実装** | `board/recalibration.py`の`assess_recalibration_need()`。詳細は次節。 |

## 新規実装：再キャリブレーション判定（`src/dartsanalytics/board/recalibration.py`）

指示書§7の「精度低下時には再キャリブレーションを促す」に対応する機能が
存在しなかったため、今回追加した。2つの独立したトリガーのいずれかで
「再キャリブレーションを推奨」と判定する：

1. **confidence低下トリガー**：今回のキャリブレーション自体のconfidenceが
   絶対的に低い（デフォルト閾値0.5未満）、または直前の「最後に良好だった
   キャリブレーション」から大きく低下した（デフォルト閾値0.2）場合。
2. **ズレ（drift）トリガー**：中心座標・半径が直前の良好なキャリブレー
   ションから正規化して大きくズレている場合（デフォルト閾値：中心5%、
   半径10%、いずれも前回半径に対する比率）。**confidence自体は高いままでも**
   このトリガーは反応する — 「カメラや盤がわずかに動いたが、検出アルゴ
   リズム自体は自信満々に間違った位置を検出している」という、confidence
   だけでは検知できない危険なケースをカバーするため。

4つの閾値定数はいずれも**実測に基づく較正値ではなく、明示された上書き
可能な慣習値**である（`board.grouping.DEFAULT_BULL_VICINITY_RADIUS`と
同じ設計方針 — 「解析不能なものを無理に判定しない」の一環として、
「測定値であるかのような虚偽の精度」を主張しないため）。

テスト7件で以下を確認済み（`tests/test_recalibration.py`）：
- 変化なし（微小なジッター程度）では推奨しない
- 絶対confidenceが閾値未満なら単独で推奨
- confidenceが閾値を超えて低下すれば（絶対値はまだ問題なくても）推奨
- 中心のズレのみ（confidence変化なし）でも推奨
- 半径のズレのみでも推奨
- 閾値のカスタマイズが正しく反映される

## 直接測定値・計算値・推定値・助言の区別

`BoardCalibration`は`data_kind: DataKind = DataKind.ESTIMATED`を既定値と
して持ち（Phase 3から変更なし）、`require_confidence_for_estimate`により
confidence無しでESTIMATEDを作ることはできない（バリデーション済み）。
これにより「キャリブレーション結果は推定値であり、直接測定値ではない」
ことがデータモデルレベルで強制されている。

## 既知の未対応・制約（今回新たに整理）

- 上表の「未実装」項目（board plane/segment boundary/homography/lens
  distortion/camera parameters）は、いずれもPhase 3のスコープ外として
  意図的に先送りされたものであり、今回のセッションでも実装しなかった。
  理由：(a) 実際のダーツボード・カメラでの検証データが本セッションには
  無く、これらの高度な幾何補正を実データ無しに実装すると「未検証の
  補正ロジックを検証済みのように見せる」リスクがある、(b) 指示書§14の
  停止条件（外部仕様不明で推測実装になる）に近い性質を持つため、
  実データ入手後に着手するのが適切と判断した。
- `assess_recalibration_need()`はロジック単体としては実装・テスト済み
  だが、実際のセッションフロー（前回の良好なキャリブレーションをDBから
  取得し、新しいキャリブレーションと比較し、UIに促す）への結線はまだ
  行っていない（`SessionRecordingService`にまだキャリブレーション系
  ユースケースの呼び出し例が無い — §10のservice層は`record_board_
  calibration`という保存用メソッドのみで、再キャリブレーション判定と
  組み合わせた呼び出しパターンは未実装）。

## 結論

盤中心・半径の簡易キャリブレーションと結果の永続化（§10と連携）は実装
済み。「精度低下時の再キャリブレーション促し」は今回新規実装し、テストで
検証した。homography・レンズ歪み補正・カメラパラメータ推定・盤面傾き
補正・セグメント境界整列は未実装であり、実データでの検証を経てから
着手すべき項目として明記する。310件のテストが全て合格（新規7件を含む）。
